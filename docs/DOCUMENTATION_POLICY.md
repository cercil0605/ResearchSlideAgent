# 文書更新ルール

文書はコードと別に放置する成果物ではありません。利用者が見る動作や、開発者が頼る契約を変えた場合は、変更と同じ作業で関連文書を確認・更新します。

## 変更と確認する文書

| 変更内容 | 確認・更新する文書 |
|---|---|
| 利用者の目的、制作の流れ、生成結果の意味 | [製品仕様](PRODUCT_SPEC.md)、[利用シーン](USER_USE_CASES.md) |
| 対応形式、図表、容量、枚数、保持期間、修正範囲 | [機能と制約](CAPABILITIES.md)、必要に応じて[利用シーン](USER_USE_CASES.md) |
| MCPツール、HTTP、SlideSpec、JSON Schema、エラー | [API](../API.md)、`schemas/`、examples、MCPテスト |
| サービス構成、キュー、保存方式、処理フロー | [Architecture](../ARCHITECTURE.md) |
| 認証、権限、信頼境界、ファイルの安全性 | [Security](../SECURITY.md)、[認証手順](../deploy/AUTH.md) |
| 起動、環境変数、Portainer、更新・復旧 | [README](../README.md)、`deploy/`の該当手順 |
| 機械検査、受入手順、検証済み／未検証の主張 | [Testing](../TESTING.md)、必要に応じて互換性資料 |
| 発表内容・引用・説明粒度のルール | Plugin Skillの`references/`。`docs/`には複製しない |
| 重要な技術判断や方針変更 | `docs/adr/`。旧判断を置き換える場合は状態と後継ADRを記す |

## 更新時の確認

1. 変更した挙動を、モデル、API、生成処理、設定、テストのうち該当する実装で確かめる。
2. 上の対応表と[文書案内](README.md)を使い、関係する資料を洗い出す。
3. 数値制限や「対応／未対応」の記述は、Schemaや実装だけでなくテストとも照合する。
4. 現行仕様、導入手順、制約、検証済みの主張が相互に矛盾していないか読む。
5. 文書を変えない場合は、変更の要約に理由を書く。

## 正本の扱い

- APIの契約は`API.md`とSchema、実際の動作はコードとテストを正本とする。
- ChatGPTが制作時に使うルールはPlugin Skillの`references/`を正本とする。
- ユーザー向けの現在の説明は`docs/PRODUCT_SPEC.md`と`docs/CAPABILITIES.md`に集約する。
- `docs/README.md`で履歴資料に分類した文書は、現行コードと記述が違っても現行仕様を上書きしない。
- READMEや複数文書に同じ数値・詳細手順を重ねて記載しない。入口では短く案内し、正本へリンクする。
